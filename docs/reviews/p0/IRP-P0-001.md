## 3. Approved architecture baseline

### Tenant and authorization

- Buyer and Seller are separate tenants.
- Supplier uses a hybrid model: independent tenant identity, with operational access through explicit transaction/site assignments.
- Tenant-owned users, memberships, sites, warehouses, and internal data remain isolated.
- Transactions explicitly identify Buyer and Seller participants.
- Cross-tenant access requires explicit relationship and permission.
- Server-side authorization is authoritative and fail-closed.
- Membership, role, resource ownership, transaction relationship, and site assignment must be validated.
- Legacy data without reliable ownership evidence is quarantined; ownership must not be inferred from email, organization name, tracking code, or creator identity.

### Sources of truth and governance

- Signed contract snapshot: contractual agreement.
- Payment ledger: financial settlement.
- Evidence register: fulfillment evidence.
- Server-side authorization: goods-release authority.
- Transaction scope activation/reactivation requires bilateral approval.
- Before contract signing, either party may unilaterally suspend or withdraw consent for its scope.
- Release approval is condition-based, not blanket bilateral approval.
- Seller Authorized Representative issues/confirms release instruction.
- Buyer approval is required only where the signed contract snapshot or applicable law makes it a release condition.
- Syariah Reviewer may review, comment, and recommend; this role does not automatically approve transactions, alter the ledger, or authorize goods release.

## 9. Evidence reconciliation addendum — 2026-11-10

The source-pinned register is [EVIDENCE-RECONCILIATION-001](./EVIDENCE-RECONCILIATION-001.md). It records exact repository, branch, commit SHA, file path, blob SHA, and line anchors for the material findings.

### Confirmed source-level conclusions

1. Mobile main `0a3c595c6697f56d0cef8536c3b93c3886cc5ab1` still reads `SINGLE_ENTERPRISE_ID`, exposes `/api/v1/enterprise/session`, and delegates tenant enforcement to the enterprise authorization helper (EV-MOB-001/002).
2. Mobile transaction create, transaction status update, and tenant sync return 410 at the pinned source (EV-MOB-001).
3. The transaction list/detail GET handlers are registered in both `server/supply-chain-routes.mjs` and `server/index.mjs`. The supply-chain route registration is called first (EV-MOB-003). BLK-004 is therefore a confirmed source discrepancy, not merely a suspected duplicate.
4. The five schema gaps are recorded by the source reconciliation and asserted by the schema-contract test source (EV-MOB-005/006). Test source is not a test execution result.
5. The Mobile tenant migration script exists, but the package API startup script is `node server/index.mjs`; no invocation of the tenant migration script is evidenced in that startup path (EV-MOB-004). The deployed runtime entrypoint remains unverified.
6. Web source includes tenant/transaction routes, while its checked-in OpenAPI document describes only health, products, inquiries, tracking, and inquiry sync (EV-WEB-001/002).
7. Web and Desktop each have tenant migration scripts, but their package scripts do not establish an automatic startup migration path (EV-WEB-003/EV-DESK-001).

### Cross-document reconciliation

- AUTH-MOBILE-RECONCILIATION-001 is the approved architecture target at Mobile docs branch commit `df929720ecec6e8eade19a532287c222b8e54945`; it explicitly does not authorize implementation.
- Its NEG-001–NEG-030 / POS-001–POS-012 identifiers are architecture test contracts. The integrated UI-NEGATIVE-ACCESS-TEST-001 uses its own NAX/PAX identifiers and now contains an explicit crosswalk. Neither set is evidence of execution.
- Supplier hybrid is already an approved design baseline. OD-007's earlier wording (“Must Supplier always be an independent tenant?”) conflicts with that baseline and must be reframed in the subsequent OD review as an implementation-detail question, not reopened as an undecided architecture principle.
- The current screen/API matrix maps screen families and ID ranges, not all 38 individual screen IDs to exact endpoint contracts. This remains an explicit High review gap; it must be completed or formally deferred with an owner before final package approval.
